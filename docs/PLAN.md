# «Цели и конверты» — поэтапный план разработки

Рабочее название. Веб-приложение (PWA) для обычного человека: бюджет «план–факт», финансовые цели с расчётом взносов, финансовый резерв, баланс семьи. Позже — налоговые вычеты, финплан, десктоп и мобильная версия.

Основа методики — курс «Финансовая грамотность» (модули 2–8). Все примеры курса пересчитаны скриптом, план прошёл независимое ревью; найденные ошибки исправлены (раздел 8). Версия плана: 1.2 (сентябрь 2026) — добавлен настраиваемый дашборд из виджетов на вкладке «Обзор».

---

## 1. Принципы продукта

1. **Будущее, а не только прошлое.** Главный вопрос пользователя: «Хватит ли мне денег на цель и сколько откладывать в месяц?» Учёт трат — средство, а не цель.
2. **Одна модель данных — много вкладок.** Операция во вкладке «Бюджет» сразу меняет свободный остаток во вкладке «Цели» и показатели на «Обзоре».
3. **Local-first.** Данные хранятся на устройстве. Своего сервера на MVP нет.
4. **Постепенное раскрытие.** В первый день пользователь видит 3 вкладки: Обзор, Бюджет, Цели. Остальные открываются после онбординга или через «Ещё».
5. **Не инвестиционный советник.** Приложение считает и объясняет, но не рекомендует конкретные ценные бумаги, фонды или брокеров (индивидуальные инвестиционные рекомендации регулируются 39-ФЗ). Распределение по классам активов подаётся как обучающий пример. Везде — дисклеймер.
6. **Нормативы — в конфиге, а не в коде.** Лимиты вычетов, ставки НДФЛ, лимит страхования вкладов — в версионируемом файле правил по годам со ссылкой на источник и датой проверки.

**Сознательно вне MVP:** мультивалютность (поле `currency` есть, но разрешён только RUB), подключение к банкам, синхронизация, семейный доступ, инвестиционный учёт по бумагам.

## 2. Технологический стек

- **Язык и сборка:** TypeScript (strict), Vite, React 18.
- **UI:** Tailwind CSS + shadcn/ui (Radix). Графики — Recharts. Перетаскивание виджетов — dnd-kit (работает и мышью, и пальцем).
- **Роутинг:** React Router; вкладки = маршруты (`/overview`, `/budget`, `/goals`, `/balance`, `/deductions`, `/plan`, `/settings`).
- **Хранилище (веб и десктоп):** Dexie.js (IndexedDB) + `dexie-react-hooks` (`useLiveQuery`). Доступ только через слой репозиториев — чтобы на мобильной версии заменить на SQLite без переписывания UI.
- **Валидация:** Zod (сущности, импорт/экспорт).
- **Даты:** date-fns, локаль `ru`. Даты операций — строки `YYYY-MM-DD`, месяцы — `YYYY-MM`, без часовых поясов.
- **Импорт:** PapaParse (CSV) + определение кодировки (UTF-8 / Windows-1251 через `TextDecoder`). XLSX — ExcelJS, **только динамическим `import()`** (библиотека тяжёлая).
- **PDF (этап 8):** pdfmake со встроенным шрифтом с кириллицей, загрузка динамически.
- **PWA:** vite-plugin-pwa в режиме `registerType: 'prompt'` (пользователь сам подтверждает обновление).
- **Тесты:** Vitest (ядро — покрытие ≥ 95 %), Testing Library, Playwright (e2e), `fake-indexeddb` для тестов хранилища.
- **Качество:** ESLint, Prettier, `tsc --noEmit`, GitHub Actions (lint → typecheck → test → build → e2e).
- **Позже:** Tauri 2 (десктоп), Capacitor + `@capacitor-community/sqlite` (мобильные).

**Деньги:** целые копейки (`amountMinor: number`, integer). Прогнозы (будущая стоимость, взносы) считаются в `number` и округляются до копеек (half-up, `Math.round`) только при сохранении и отображении. Форматирование — `Intl.NumberFormat('ru-RU', { style: 'currency', currency: 'RUB' })`.

## 4. Модель данных (v1)

- **Settings:** `inflationRate` (0.08), `defaultReturnRate` (0.10), `reserveTargetMonths` (6), `onboardingDone`, `lastBackupAt`, `schemaVersion`.
- **Account — единая сущность для активов и долгов:**
  - общие поля: `id, name, side` (`asset | liability`), `type`, `currency` (только `RUB` на MVP), `openingBalanceMinor`, `openingDate`, `archived`;
  - `openingBalanceMinor` — остаток на начало дня `openingDate`. Операции раньше этой даты — история: в бюджете они учитываются, остаток счёта не меняют (уточнено 16.09.2026);
  - типы активов: `cash | debit | savings | deposit | brokerage | iis | realty | vehicle | business | other_asset` (`business` — доля в бизнесе, с версии 0.16.2); признак `isLiquid` (по умолчанию true для `cash | debit | savings`);
  - типы долгов: `credit_card | mortgage | consumer | car | other_debt`; поля `rate`, `monthlyPaymentMinor`, `endDate?`, `creditLimitMinor?`, `gracePeriodEnd?`;
  - для вкладов: `rate`, `maturityDate`, `bankName` (для проверки лимита страхования).
  - **Текущий остаток не хранится**, а считается: `openingBalance + операции`. Ручная правка остатка создаёт операцию `adjustment`. Для недвижимости и авто — операции `revaluation`.
- **Category:** `id, name, kind` (`income | expense`), `group` (обязательные / переменные), `icon`, `archived`. Стартовый набор — из шаблона бюджета курса (2.9).
- **Transaction:** `id, date, amountMinor` (всегда > 0), `kind`:
  - `income` — доход (нужен `categoryId`, `accountId`);
  - `expense` — расход (нужен `categoryId`, `accountId`; `accountId` может быть кредитной картой — тогда растёт долг);
  - `refund` — возврат покупки (уменьшает расходы своей категории);
  - `transfer` — перевод между своими счетами, в том числе погашение кредитки и пополнение вклада (`accountId` → `toAccountId`); **в доходы и расходы не входит**;
  - `adjustment` / `revaluation` — корректировка остатка или переоценка актива; в доходы и расходы не входит.
  - дополнительно: `note`, `importBatchId?`, `importRowHash?`.
  - Проценты и основной долг по кредиту: платёж делится на `expense` (проценты, категория «Проценты по кредитам») + `transfer` (основной долг). Упрощённый режим: весь платёж — `transfer`, остаток долга правится через `adjustment`.
- **BudgetPlan:** `month (YYYY-MM), categoryId, amountMinor`.
- **Goal:** `id, name, priority` (целое, **меньше = важнее**; резерв всегда 0), `kind` (`reserve | purchase | education | pension | other`), `costMinor`, `costAsOf (YYYY-MM)` — месяц, в ценах которого указана стоимость, `targetMonth (YYYY-MM)`, `returnRate`, `inflationRate`, `status` (`active | paused | done`).
- **Envelope (конверт):** `goalId, accountId, amountMinor` — часть остатка счёта, закреплённая за целью. Взнос в цель = перевод на счёт + увеличение конверта (или только увеличение конверта, если деньги уже на счёте). Конверт кладётся только на счёт с деньгами: не на `realty | vehicle | business` — имущество стоит денег, но они не отложены; конверт, оставшийся на таком счёте с прежних версий, в накопления цели не входит.
- **DashboardLayout:** `id, name, items[]`, где элемент — `{ instanceId, widgetType, size: 'S' | 'M' | 'L', order, settings }` (например, `settings.goalId` для виджета конкретной цели). Отдельные раскладки для узкого (телефон) и широкого экрана не храним: на узком экране виджеты идут в один столбец в том же порядке.
- **InsurancePolicy (этап 6):** `id, type, insurer, sumInsuredMinor, premiumMinor, endDate`.
- **MonthlySnapshot (этап 6):** `month, assetsMinor, liabilitiesMinor` — для графика капитала.
- **Document (этап 7):** `id, year, category, blob, fileName, sizeBytes, note`.

**Инварианты (проверяются в репозиториях и тестах):**
- сумма конвертов по счёту ≤ остаток счёта;
- конверт — только на счёте с деньгами (не на недвижимости, автомобиле, доле в бизнесе);
- переводы, корректировки и переоценки не влияют на доходы, расходы и свободный остаток;
- у цели «резерв» нет даты, стоимость = `reserveTargetMonths × средние расходы`.

## 5. Финансовое ядро — формулы (единый источник истины)

Обозначения: `r` — годовая доходность, `i = r / 12` — месячная ставка (номинальная, как `ПЛТ` в Excel и в курсе), `π` — годовая инфляция, `S` — текущие накопления цели (сумма её конвертов на счетах с деньгами), `C` — стоимость цели в ценах месяца `costAsOf`.

1. **Месяцы между датами:** `months(a, b) = (год_b − год_a) × 12 + (мес_b − мес_a)`.
2. **Будущая стоимость цели:** `FV = C × (1 + π)^(months(costAsOf, targetMonth) / 12)`.
3. **Оставшийся срок:** `n = months(текущий_месяц, targetMonth)`; если `n ≤ 0` и цель не достигнута — статус «срок прошёл», взнос не считается.
4. **Ежемесячный взнос (платёж в конце месяца), пересчитывается каждый месяц от фактических накоплений:**
   `PMT = (FV − S × (1 + i)^n) × i / ((1 + i)^n − 1)`;
   при `i = 0`: `PMT = (FV − S) / n`;
   если `S × (1 + i)^n ≥ FV` → `PMT = 0`.
   Стартовый капитал тоже приносит доход — в Excel-шаблоне курса это не учтено (см. 8.1).
5. **Срок при заданном взносе:** **линейный перебор** `n = 1…1200`, первый `n`, при котором
   `S × (1+i)^n + P × ((1+i)^n − 1) / i ≥ C × (1+π)^((months(costAsOf, текущий_месяц) + n) / 12)` (при `i = 0` вместо дроби — `n`).
   Бинарный поиск не годится: условие не монотонно по `n` (цель дорожает с инфляцией и может снова «убежать»). Не нашлось за 1200 мес. — «недостижима при таком взносе».
6. **Реальная доходность:** `r_real = (1 + r) / (1 + π) − 1`. Предупреждение, если `(1 + i)^12 ≤ 1 + π`.
7. **Свободный остаток месяца:** `доходы − (расходы − возвраты)`; переводы не учитываются. План и факт считаются отдельно; годовой — сумма по месяцам.
   **Обычный месяц** — база для выводов, которые не должны зависеть от числа, в которое их читают: тип бюджета, кредитная нагрузка (формула 10), распределение по целям (формула 8). Это среднее доходов и расходов за последние полные месяцы (не больше 3), считая с первого месяца с операциями; если таких месяцев нет — план текущего месяца; если нет и плана — текущий месяц как есть. Экран месяца в «Бюджете» по-прежнему показывает сам месяц. (Уточнено 16.09.2026: 16-го числа зарплата уже пришла, а аванс ещё нет, и один и тот же бюджет выглядел то дефицитным, то профицитным.)
8. **Распределение по целям:** к распределению — `свободный остаток обычного месяца − основной долг по графику`, где `основной долг = сумма monthlyPayment по долгам − средние проценты из категории «Проценты по кредитам»` (не меньше 0): основной долг не расход, но и не свободные деньги. Первым получает резерв, пока он ниже нормы: `min(10 % дохода обычного месяца, сколько не хватает до нормы)`. Затем активные цели по возрастанию `priority`; каждой выделяется `min(остаток, PMT)`. При нехватке — дефицит по каждой цели и подсказки: срок (формула 5), сумма, доходность (с предупреждением о риске).
9. **Финансовый резерв:** `резерв = ликвидные_счета − конверты_других_целей_на_ликвидных_счетах` (деньги цели на брокерском счёте или вкладе в ликвидные счета не входили и из резерва не вычитаются); `месяцев = резерв / средние_расходы`. Средние расходы — факт последних полных месяцев (не больше 3), делённый на число месяцев от первого месяца с расходами: у того, кто ведёт учёт первый месяц, это расходы этого месяца, а не их треть; если факта нет — план текущего месяца. Норма 3–6 месяцев (курс 2.5). Рекомендуемый взнос в резерв до достижения нормы — 10 % дохода (курс 2.5), пользователь может изменить.
10. **Кредитная нагрузка:** `сумма monthlyPayment по долгам / доход обычного месяца после НДФЛ` (формула 7). До 25 % — норма, 25–30 % — внимание, > 30 % — напряжённая ситуация (курс 2.3). Для кредиток без графика — `monthlyPaymentMinor` вводит пользователь (минимальный платёж).
11. **Собственный капитал:** `активы − обязательства`; < 0 — красный статус.
12. **Пенсионный капитал (этап 8):** через реальную доходность, выплаты в начале года, индексируются на инфляцию:
    - «жить на доход, сохраняя капитал»: `K = A × (1 + r_real) / r_real`;
    - «проесть капитал за T лет»: `K = Σ_{k=0}^{T−1} A × (1+π)^k / (1+r)^k`;
    где `A` — годовой расход на пенсии в ценах года выхода за вычетом государственной пенсии.

## 6. Этапы

Оценки — для одного разработчика с Claude Code, ориентир, а не обязательство.

### Этап 0. Каркас проекта (1–2 дня)
- Vite + React + TS strict, Tailwind, shadcn/ui, React Router, ESLint/Prettier, Vitest, Playwright, GitHub Actions.
- Оболочка: боковое меню на десктопе, нижняя панель на мобильном (≤ 768 px, до 5 пунктов + «Ещё»); вкладки-заглушки; светлая/тёмная тема; русская локаль.
- vite-plugin-pwa (`prompt`), манифест, офлайн-кэш.
- **Готово, когда:** CI зелёный; приложение устанавливается как PWA и открывается офлайн.

### Этап 1. Финансовое ядро (3–5 дней)
- `core/*` по формулам раздела 5 (кроме пенсии и образования).
- Все тестовые векторы + граничные случаи: `n ≤ 0`, `i = 0` при `π > 0`, `S ≥ FV`, отрицательные и нецелые копейки (ошибка), `n = 1200`, пустые данные для средних расходов.
- **Готово, когда:** покрытие `core/` ≥ 95 %, все векторы проходят.

### Этап 2. Хранилище, счета и надёжность данных (4–5 дней)
- Dexie-схема v1, репозитории с Zod-валидацией и проверкой инвариантов.
- **Минимальный CRUD счетов** (нужен операциям и «Обзору» уже на этапе 3).
- Обработка `versionchange` в Dexie (закрыть соединение, попросить перезагрузить) — иначе старая вкладка блокирует миграцию.
- `navigator.storage.persist()` при первом запуске, статус в настройках.
- **Предупреждение про Safari:** данные сайта, открытого во вкладке Safari, могут быть удалены после 7 дней без посещений; установленное на экран «Домой» приложение под это правило не попадает. Показывать инструкцию по установке на iOS/macOS.
- Экспорт/импорт всех данных в JSON (с `schemaVersion`), проверка при импорте, режим «заменить» с подтверждением; опционально — шифрование файла паролем (WebCrypto, AES-GCM + PBKDF2).
- Напоминание о резервной копии раз в 30 дней.
- Синхронизация между открытыми вкладками браузера (BroadcastChannel + `useLiveQuery`).
- **Готово, когда:** e2e «данные → экспорт → очистка → импорт → совпадают» проходит; изменение в одной вкладке видно в другой; тест миграции v1 → v2 (фиктивной) проходит.

### Этап 3. Онбординг и «Обзор»-дашборд (5–6 дней)
- Анкета из 5 шагов: доход после налогов → обязательные расходы → переменные расходы → счета (ликвидные накопления) и долги → первая цель. Можно пропустить.
- Создание стартовых категорий, цели «Финансовый резерв», первой цели.
- **«Обзор» — дашборд из виджетов:**
  - реестр виджетов `features/overview/widgets/registry.ts`: у каждого — `type`, название, описание, допустимые размеры, компонент, Zod-схема настроек, «пустое состояние» (что показать, если данных нет, и кнопка «заполнить»);
  - **готовая раскладка по умолчанию** после онбординга — пользователь не видит пустой экран;
  - режим «Настроить»: добавить виджет из каталога, удалить, перетащить (dnd-kit), выбрать размер S / M / L, «Сбросить к стандартному»;
  - сетка: 4 колонки на широком экране (S = 1, M = 2, L = 4 колонки), 2 — на планшете, 1 — на телефоне; порядок общий;
  - виджеты этапа 3: «Свободный остаток месяца», «Резерв X из 6 мес.», «Прогресс цели» (настройка — какая цель), «Все цели», «Собственный капитал», «Кредитная нагрузка», «Предупреждения», «Быстрый ввод операции»;
  - виджеты добавляются в каталог на следующих этапах: «План–факт по категориям» и «Расходы по категориям» (этап 4), «Что если» по цели (этап 5), «Скоро: сроки», «Динамика капитала» (этап 6), «Вычеты: можно вернуть» (этап 7);
  - ошибка в одном виджете не ломает дашборд (Error Boundary на каждый виджет).
- **Готово, когда:** e2e-тест проходит онбординг с типовыми данными (≤ 25 действий) и видит расчёт «сколько откладывать и хватает ли бюджета»; добавление, перестановка, смена размера и удаление виджета сохраняются после перезагрузки; на ширине 375 px дашборд в один столбец без горизонтальной прокрутки.

### Этап 4. «Бюджет» (5–7 дней)
- Операции: добавление за 2 касания (сумма → категория), все виды из раздела 4, редактирование, удаление, поиск, фильтры.
- План по категориям на месяц, копирование плана с прошлого месяца.
- Вид «месяц» (план / факт / отклонение) и «год» (12 месяцев + итог), как в шаблоне курса.
- **Готово, когда:** месячный и годовой итоги совпадают с ручным расчётом на тестовом наборе (с переводами, возвратами и тратами по кредитке).

### Этап 4b. Импорт выписок (5–7 дней)
- CSV (UTF-8 и Windows-1251, разделители `;` и `,`, десятичная запятая, суммы со знаком или отдельными колонками), XLSX (ExcelJS, динамическая загрузка).
- Мастер: выбор счёта → сопоставление колонок → предпросмотр → правила автокатегоризации по ключевым словам → подтверждение.
- Дубли: хэш исходной строки выписки (`importRowHash`); совпадения по «дата + сумма» без совпадения хэша — не отбрасываются, а помечаются «возможный дубль» для ручного решения.
- Отмена импорта целиком (`importBatchId`).
- **Готово, когда:** повторный импорт того же файла не создаёт дублей; две одинаковые покупки за день из одной выписки сохраняются обе; тестовые выписки в cp1251 читаются корректно.

### Этап 5. «Цели» (5–7 дней)
- CRUD целей, приоритеты (перетаскивание), пауза, «достигнута».
- Конверты: закрепление части остатка счёта за целью, контроль инварианта.
- Карточка цели: стоимость сегодня → в будущем, взнос в месяц/год (пересчёт от фактических накоплений), прогресс, реальная доходность, график.
- Распределение свободного остатка (формула 8), дефицит, подсказки.
- «Что если»: ползунки срока, суммы, доходности — пересчёт на лету, сохранение только по кнопке.
- **Готово, когда:** векторы воспроизводятся через интерфейс; пропуск взноса увеличивает взнос в следующем месяце; резерв не считает деньги из конвертов других целей.

### Этап 6. «Баланс» (3–4 дня)
- Полный интерфейс счетов, долгов, страховых полисов.
- Ежемесячные снимки капитала и график.
- Лента «Скоро» на «Обзоре»: льготный период кредиток, окончание вкладов и полисов.
- Предупреждение, если на вкладах в одном банке больше лимита страхования (значение из конфига нормативов).
- **Готово, когда:** капитал и кредитная нагрузка совпадают с ручным расчётом.

### Нефункциональные требования к MVP
- 10 000 операций: открытие «Бюджета» и пересчёт «Обзора» ≤ 500 мс на среднем ноутбуке; тест с генерацией данных.
- Размер начального JS ≤ 300 КБ gzip (ExcelJS и pdfmake — отдельными чанками).
- Работа офлайн, доступность (контраст, клавиатура, подписи полей).

### ► Релиз MVP (веб, PWA)
- Лендинг с дисклеймером и политикой конфиденциальности.
- **Аналитика — осторожно.** Любые счётчики с IP/cookie (Яндекс Метрика и т. п.) и сбор контактов для обратной связи — это уже обработка персональных данных: уведомление Роскомнадзора, отдельное согласие, локализация в РФ, запрет на иностранные сервисы без оформления трансграничной передачи. Для пилота проще: без счётчиков, обратная связь — через анкету, куда пользователь сам решает, что написать; метрики — добровольная выгрузка обезличенной статистики.
- Пилот на 10–20 пользователях: доля прошедших онбординг, создавших цель, вернувшихся через 7 и 30 дней.
- **Решение о следующих этапах — по итогам пилота.**

### Этап 7. «Вычеты» (5–7 дней)
- `core/rules/2026.ts` и далее по годам: лимиты и ставки со ссылкой на источник и датой проверки.
- Анкета «что мне положено»: дети, обучение, лечение, спорт, ИИС-3, ипотека, покупка/продажа жилья.
- Сумма к возврату с учётом лимитов и ставки НДФЛ пользователя; срок давности 3 года.
- Хранение чеков и договоров (Blob в IndexedDB, лимит размера файла, индикатор занятого места).
- Чек-лист документов (урок 3.7), напоминание в январе.
- **Готово, когда:** расчёты совпадают с примерами ФНС текущего года; у каждого норматива есть источник.

### Этап 8. «Финплан» (7–10 дней)
- Мастер из 8 шагов урока 2.7.
- Калькуляторы «Образование» (поток расходов по годам учёбы) и «Пенсия» (коэффициент замещения 70 %, государственная пенсия, возраст дожития, две стратегии — формула 12).
- Структура портфеля по профилю риска — только классы активов, как обучающий пример.
- Экспорт в PDF (pdfmake), напоминание о пересмотре раз в квартал и год.
- **Готово, когда:** пенсионные векторы проходят; PDF с кириллицей открывается и печатается.

### Этап 9. Десктоп — Tauri 2 (4–6 дней)
- Та же сборка в webview. IndexedDB в webview привязан к origin: **зафиксировать схему/origin и идентификатор приложения до первого релиза**, иначе при их смене данные «пропадут». Тест: обновление версии не теряет данные.
- Экспорт/импорт через системный диалог; автообновление; подпись сборок (Windows/macOS).
- **Готово, когда:** установщик ставится, данные переживают обновление.

### Этап 10. Мобильная версия — Capacitor (10–15 дней)
- Хранилище — SQLite (`@capacitor-community/sqlite`) через тот же слой репозиториев: IndexedDB внутри WKWebView система может очистить. Миграция данных из веб-версии — через файл экспорта.
- Android, затем iOS; локальные уведомления; вход по PIN/биометрии.
- Публикация: RuStore и Google Play; App Store — с учётом ограничений для разработчиков из РФ.
- Разбор банковских уведомлений на Android — только после проверки актуальных правил магазинов.
- **Готово, когда:** приложение опубликовано хотя бы в одном магазине.

### Этап 11. Синхронизация (по итогам пилота)
- Сквозное шифрование на клиенте, сервер в РФ.
- Даже зашифрованные данные остаются персональными: нужны уведомление РКН, политика обработки, отдельное согласие. Чеки на лечение — данные о здоровье (специальная категория, ст. 10 152-ФЗ) — отдельное письменное согласие или не синхронизировать их вовсе.
- До запуска — консультация юриста.

## 8. Проверка плана: что найдено и как учтено

Проверка шла в два шага: пересчёт всех примеров курса скриптом и независимое ревью версии 1.0 плана.

### 8.1. Ошибки и упрощения в материалах курса

1. **Стартовый капитал без процентов (шаблон 2.9, урок 2.4).** В формуле `ПЛТ(…; ; FV − S)` стартовый капитал вычитается, будто 5 лет лежит без дохода. Взнос курса 45 339 ₽, правильно — 39 505 ₽ (завышение на 14,8 %). → Формула 4.
2. **Пенсионный капитал через номинальную доходность (урок 7.4).** `240 032 × 12 / 8,73 % ≈ 33,0 млн ₽` даёт доход 240 тыс./мес. **без индексации**; при инфляции 6,9 % его покупательная способность падает вдвое примерно за 10 лет. Корректно (выплаты в начале года, индексируются): «жить на доход» ≈ **171 млн ₽**, «проесть за 20 лет» ≈ **49 млн ₽**. → Формула 12 и векторы.
3. **Устаревшие нормативы (курс 2021–2022).** Проверено на сентябрь 2026:
   - социальные вычеты — общий лимит **150 000 ₽** (было 120 000); обучение ребёнка — **110 000 ₽** (было 50 000); дорогостоящее лечение — без лимита;
   - вычет на детей — **1 400 / 2 800 / 6 000 ₽**, ребёнок-инвалид — 12 000 ₽; лимит дохода — **450 000 ₽** (было 1 400 / 1 400 / 3 000 и 350 000);
   - НДФЛ — прогрессивная шкала 13–22 % вместо 13/15 %;
   - ИИС типов А и Б не открываются; ИИС-3: вычет на взносы до 400 000 ₽ в год, на доход — до 30 млн ₽, минимальный срок 5 лет с ростом до 10;
   - страхование вкладов — **1,4 млн ₽**, в отдельных случаях (эскроу, продажа жилья, наследство и др.) — до 10 млн ₽.
   → Конфиг `core/rules/<год>.ts`; перед релизом этапа 7 — повторная сверка с nalog.gov.ru и КонсультантПлюс.
4. **Месячная ставка.** Курс использует номинальную `r / 12`; с ней примеры 7.3 совпадают до рубля. → Оставляем, пишем в подсказке.
5. **Образование как разовая сумма (урок 7.3).** Консервативное упрощение. → MVP так же, этап 8 — поток по годам.
6. **Уроки 6.3, 6.4, 6.6** (фонды 2022 года, иностранное страхование, доллар для долгих целей) устарели и близки к рекомендациям. → В продукт не переносятся.

### 8.2. Замечания независимого ревью версии 1.0 и исправления

1. **Критично — поиск срока бинарным поиском некорректен** (условие немонотонно). → Линейный перебор, добавлен вектор-контрпример.
2. **Критично — цифра «≈45 млн» для пенсии посчитана по смешанной схеме.** → Исправлено на ≈49 млн (начало года), схема зафиксирована, числа внесены в векторы.
3. **Критично — двойной учёт целей** (взнос как расход + распределение остатка; привязанный счёт одновременно в резерве и в цели). → Взнос = перевод, переводы вне доходов/расходов; введены конверты; резерв = ликвидные счета минус конверты других целей.
4. **Важно — взнос не пересчитывался от фактических накоплений; не было даты цены.** → Поле `costAsOf`, ежемесячный пересчёт; задано поведение цели «резерв».
5. **Важно — пробелы модели:** кредитка не могла быть счётом операции, не было возвратов, ручной остаток расходился с операциями, дубли при импорте отбрасывали реальные одинаковые траты, не учитывалась кодировка cp1251. → Единая сущность `Account`, виды `refund/adjustment/revaluation`, расчётный остаток, хэш строки выписки, определение кодировки.
6. **Важно — хранилище:** Safari удаляет данные сайта через 7 дней без посещений, WKWebView в Capacitor может очистить IndexedDB, в Tauri данные привязаны к origin, старая вкладка блокирует миграцию, ExcelJS тяжёлый. → Предупреждение и установка PWA, SQLite на мобильных, фиксация origin, обработка `versionchange`, динамическая загрузка.
7. **Важно — порядок этапов:** счета нужны раньше этапа 6. → Минимальный CRUD счетов перенесён в этап 2.
8. **Важно — сроки занижены** (импорт, мобильная версия). → Импорт выделен в этап 4b, мобильная версия 10–15 дней, добавлен RuStore; добавлены нефункциональные требования.
9. **Важно — 152-ФЗ:** аналитика с IP/cookie на пилоте — уже обработка ПД; данные о лечении — специальная категория. → Уточнено в релизе MVP и этапе 11.
10. **Мелочь — шкала приоритетов, режим округления, база для кредитной нагрузки.** → Явно заданы.

### 8.3. Решение о дашборде (версия 1.2)
- Дашбордом становится только «Обзор». Ввод операций, план бюджета и настройка целей остаются отдельными экранами: в виджете неудобно редактировать таблицы.
- Главный риск для «простого человека» — пустой экран и лишняя настройка. Поэтому есть готовая раскладка и кнопка «Сбросить», а режим настройки не обязателен.
- Сетка с произвольными координатами и растягиванием (react-grid-layout) плохо работает на телефоне и сложнее в поддержке. На MVP — упорядоченный список виджетов фиксированных размеров S/M/L; свободная сетка — только если пилот покажет спрос.

### 8.4. Проверка на двух сценариях (16.09.2026, версия 0.16.2)
Приложение прошли за двух людей — предпринимателя с капиталом 445 млн ₽ и рабочего с зарплатой 65 000 ₽ и долгами — через интерфейс, числа сверены с независимым пересчётом. Арифметика совпала; неверными оказались выводы. Что изменено:
1. Тип бюджета, кредитная нагрузка и распределение — по обычному месяцу, а не по текущему (формулы 7, 8, 10).
2. Резерв: из ликвидных счетов вычитаются только конверты на ликвидных счетах; средние расходы делятся на число месяцев учёта, а не всегда на 3 (формула 9).
3. Из свободных денег вычитается основной долг, резерв получает деньги первым (формула 8).
4. Операции раньше даты открытия счёта не меняют его остаток (раздел 4).
5. Ставка у долгов — в форме счёта и в знакомстве: без неё план не видел дорогих кредитов.
6. Цель «ровно эта сумма» — без инфляции.
7. Тип актива «доля в бизнесе»; конверт только на счёте с деньгами (раздел 4).
8. Вычет за жильё: остаток и «уже получено» — отдельно за стоимость и за проценты, как в 3-НДФЛ (стоимость списывается первой); схема базы 7 делит прежнюю общую сумму так же.
9. Отметка «работодатель уже дал вычет на детей» по умолчанию снята; подсказка про коды 126–149 справки о доходах.
Сценарии сохранены как e2e-регрессии (`e2e/scenarios.spec.ts`). Не сделано: рост стоимости бизнеса и недвижимости в прогнозах целей.
